# AGENTS.md — TradeVision Backend

Guidance for AI agents working in `TradeVision-backend/`. This is the Python backend
for **TradeVision** (aka SmartInvestor-Lanka), a stock-prediction system focused on the
Colombo Stock Exchange (CSE). Core features: a **news sentiment pipeline** (FinBERT),
an **XGBoost next-day return model served on live CSE data**, an AI chat assistant,
a DeepSeek deep-analysis endpoint, and per-user watchlist/portfolio.

## What this backend does

`GET /api/v1/stocks/analyze?symbol=JKH.N0000` returns, for **any** CSE ticker:
1. **News sentiment** — scrapes recent articles, scores them with FinBERT, aggregates
   one weighted score per ticker (recent news weighted higher).
2. **Price prediction** — fetches the last ~5 daily bars from the **live CSE chart
   API**, computes short-window technical indicators, runs XGBoost (an expected-return
   regressor) to get tomorrow's move, blends in sentiment post-hoc, and derives a
   predicted close from the latest CSE close.

The other routers alongside it, all serving the React frontend:

| Route | Purpose |
|---|---|
| `GET /api/v1/market/summary` | live CSE gainers / losers / most active, market status, ASPI |
| `GET /api/v1/market/quote` `/symbols` `/history` `/intraday` | one quote, all ~285 listings, ~5 daily bars for charts, today's ticks — all CSE |
| `GET /api/v1/stocks/ai-analysis` | DeepSeek deep analysis of one symbol (UI currently locked behind "coming soon") |
| `POST /api/v1/chat` | Gemini assistant (DeepSeek fallback), grounded in live data via function calling |
| `GET /api/v1/chat/status` | whether any chat model is configured |
| `/api/v1/watchlist/*`, `/api/v1/portfolio/*` | per-user watchlist & holdings (Supabase auth + Postgres) |

`/market/*` **and the prediction itself** read the CSE's own API — see the feed
split below. `/chat` needs `GEMINI_API_KEY` (or `AI_ANALYSIS_API_KEY` for the
DeepSeek fallback); without either the app still boots and that one route
returns 503.

## Tech stack

- **API**: FastAPI + Uvicorn ([api/main.py](api/main.py)).
- **ML**: `xgboost` (direction classifier), `pandas`/`numpy` (features).
- **NLP**: `transformers` + `torch` (CPU), model `ProsusAI/finbert`.
- **Training data**: `yfinance` — CSE symbols map as `JKH.N0000` → `JKH-N0000.CM`.
  Multi-year history is real; the live tail is dead (see data contract), so training
  CSVs are cut at `TRAIN_END=2026-01-31`.
- **Live market data & serving**: `requests` against `www.cse.lk/api` (POST-only,
  undocumented) — quotes, movers, charts **and** the bars the model predicts on.
- **Chat**: `google-genai` (`from google import genai`), model `gemini-2.5-flash`,
  with a DeepSeek fallback ([services/deepseek_chat.py](services/deepseek_chat.py),
  raw HTTP, shares the `AI_ANALYSIS_*` env with the deep-analysis endpoint).
- **Scraping**: `urllib` + `beautifulsoup4` (RSS); `playwright` headless Chromium (website mode).
- **Declared but unused**: `sqlalchemy`, `psycopg2-binary`, `alembic` (Postgres).
- **Python 3.11**. `PYTHONPATH=/app` — imports are rooted at the backend dir.

## THE DATA CONTRACT — two feeds, one job each

| Path | Feed | Why |
|---|---|---|
| Training (`ml/fetch_data.py` → CSVs in `ml/data/`) | Yahoo, multi-year | only Yahoo has the years of history a model needs |
| Serving (`price_data.get_prediction_history()`) | **live CSE** (`cse_api.historical_5day()`) | Yahoo's feed is dead; a prediction must anchor on a bar that actually traded |

### The Yahoo ghost-bar problem (training side)

Measured on `JKH-N0000.CM` in Aug 2026:

| Window | Rows | Days that traded |
|---|---|---|
| Last 5 years | 1271 | 1075 (85%) — healthy |
| Last 6 months | 129 | 7 (5%) — dead |

Yahoo does not stop *emitting* rows when it loses the exchange; the newest bar is
always dated today. It keeps printing the **last known close with Volume 0**,
indefinitely. The rows have correct dates, no NaNs, and plausible prices — so
nothing downstream objects. Inference used to read the **last row**, which is
exactly where the ghosts were; that is why serving moved to the CSE feed.

Training defences (in [ml/train_model.py](ml/train_model.py), applied to the raw
CSV **before** features and labels are built):

1. **`TRAIN_END` cutoff** (default 2026-01-31, env-overridable) — bars after this
   are dead feed and would poison `Return_Lag*` features and `Target_Return`
   alike. Raise it only if the feed revives.
2. **`features.drop_non_trading_rows()`** — drops every `Volume <= 0` bar.
   Shared with serving: a zero-volume row records the absence of data, not a
   quiet day.
3. **`_drop_split_artifacts()`** — with `auto_adjust=False`, a 1:5 split reads as
   a −80% daily return. `MAX_ABS_DAILY_RETURN = 0.40` catches them, and the whole
   contaminated neighbourhood goes (the label at `i-1`, plus `Return_Lag1..2` at
   `i+1`/`i+2`), not just the offending row.

A density test ("N traded days in the trailing 20") was tried and **rejected**:
at the outage boundary the window is still full of healthy history, so the first
dead bars pass it. A forward-filled bar cannot be both traded and price-changing,
which is why the volume/return checks have no boundary blind spot.

### The serving side — CSE short-memory

`get_prediction_history()` maps `companyChartDataByStock` (period=7 → the last ~5
daily bars) onto OHLCV:

- `price` → Close, `high` → High, `low` → Low, `quantity` → Volume
- **Open is not in the CSE payload — approximated as the previous Close** (first
  bar: its own close). See known limitations for the measured effect.
- `drop_non_trading_rows()` runs here too — the same shared function as training.
- `MIN_ROWS = 4`: every feature window is ≤ 3, deliberately sized so 5 CSE bars
  are enough.
- `df.attrs["stale_days"]` → the route warns when the newest bar is more than
  `STALE_AFTER_DAYS` (7) behind today.

`price_data.get_price_history()` (Yahoo, 2 years, `_trim_stale_tail`) is the
**legacy** path: no production callers, kept for `test/test_stale_data.py` and
future comparison. Do not wire it back into serving.

Run `python -m test.test_stale_data` after touching any of this. Add `JKH.N0000`
as an argument to probe the live feed too.

## THE MODEL CONTRACT — read this before touching features

[services/features.py](services/features.py) is the **single source of truth** for
feature engineering. Both `ml/train_model.py` and `services/prediction_engine.py`
import `FEATURE_COLUMNS` from it. This is deliberate: if training and serving computed
features independently they would drift, and a drifted feature produces a confident,
plausible, **wrong** prediction that nothing else in the stack can detect.

The 11 features, in positional order:

```
Open_Pct, High_Pct, Low_Pct, Rel_Volume (3-day window),
RSI_3, Return_Lag1, Return_Lag2,
SMA_3_Pct, EMA_3_Pct, MACD_Pct, MACD_Hist_Pct
```

Every window is ≤ 3 **because serving only has ~5 bars** — the CSE chart API
returns the same 5 daily bars regardless of the period requested. SMA/EMA/MACD
used to be display-only; the current artifact takes them as inputs (as `*_Pct`
ratios, scale-free). Any new feature must still work on a 4–5 bar window.

**Changing this list invalidates the trained artifact.** XGBoost matches on feature
name and raises loudly on mismatch (good — it fails rather than mispredicts), but the
model must then be retrained: `python -m ml.train_model`.

### The model is cross-sectional — do not reintroduce company identity

Two features were deliberately removed, and re-adding either would break the design:

- **`Asset_ID`** — an integer company index. Its tree splits only covered the 9
  training companies, so any other ticker had no valid value. **This was the sole
  reason the model was once limited to 9 stocks.**
- **`Log_Volume`** — `log1p(raw share count)`, ~15 for a large cap and ~9 for a thin
  counter. Same leak, less obvious: it encoded company size. Replaced by `Rel_Volume`
  (`Volume / rolling_mean(Volume, 3)`), which compares a stock to its *own* recent
  average and therefore means the same thing everywhere.

Every remaining feature is scale-free, so the model predicts **any CSE ticker**,
including ones absent from training.

### Deliberate quirks — do not "fix" without retraining

- **`Return_Lag1` is `pct_change().shift(1)`** — the return over t-2 → t-1, *not*
  yesterday. Inherited from the original training script; almost certainly unintended,
  but kept so train and serve agree. Changing it requires a retrain.
- **RSI is divided by 100** in the feature vector (0–1), while `technical_summary`
  reports it on the usual 0–100 scale.
- **Flat price series give RSI 50, not 100.** Guarding only `avg_loss == 0` (the common
  shortcut) maps a stale, unchanged series to "extremely overbought" — a real hazard on
  illiquid CSE counters. See `_rsi_from_averages`.
- **RSI_3 on ~5 bars is warm-up sensitive** — Wilder smoothing seeds from the first
  window, so the value depends on those few bars. Unavoidable with a 5-bar feed;
  `MIN_ROWS = 4` is the floor.

## Key files in `services/`

- [features.py](services/features.py) — indicators + the feature contract. `add_indicators()`,
  `add_model_features(df)`, `build_feature_row(df)`, `drop_non_trading_rows(df)`,
  `realized_volatility()`.
- [price_data.py](services/price_data.py) — `get_prediction_history(ticker)` maps
  `cse_api.historical_5day()` onto OHLCV for the model (**the serving path**; Open ≈
  previous Close). `get_price_history(ticker)` is the legacy Yahoo fetch — tests only,
  see the data contract.
- [prediction_engine.py](services/prediction_engine.py) — `StockPredictionEngine`. Loads
  the artifact (an `XGBRegressor` over expected next-day return), adds sentiment
  **post-hoc** (`expected_return += 0.005 * score`; the model has no sentiment
  input), derives the close as `latest * (1 + expected_return)`, and maps
  return-vs-volatility to a 0–100 "confidence" that is **not** a calibrated
  probability.
- [ticker_registry.py](services/ticker_registry.py) — `resolve_open()` (permissive, used by the
  route) and `resolve()` (strict). The registry supplies **company names for the news
  scraper**; it does *not* limit what can be predicted.
- [news_pipeline.py](services/news_pipeline.py) — `NewsSentimentPipeline`. `get_sentiment(ticker)`
  returns a flat dict and **never raises**; failures degrade to neutral 0.0 with a
  `status` explaining why.
- [scraper.py](services/scraper.py) — `NewsScraper`. Searches by **company name**, not ticker.
  **Always call `.close()`** (the pipeline does, in a `finally`).
- [sentiment.py](services/sentiment.py) — FinBERT wrapper. Callers **must** check `ok`; a failed
  analysis is excluded from averages rather than counted as neutral 0.0.
- [cache.py](services/cache.py) — thread-safe TTL cache used for prices, sentiment and
  CSE market lists.
- [cse_api.py](services/cse_api.py) — **live** CSE market data from `www.cse.lk/api`.
  `top_gainers()`, `top_losers()`, `most_active()`, `all_companies()`, `quote()`,
  `market_status()`, `market_indices()`, `intraday()`, and `historical_5day()` —
  which **feeds the prediction model** (see the feed split below). The only module
  that knows CSE's wire format, which is worth
  keeping in one place: every endpoint is POST-only (GET returns 405), the losers
  endpoint is spelled `topLooses`, and `tradeSummary` wraps its rows in
  `reqTradeSummery`.
- [gemini_chat.py](services/gemini_chat.py) — Gemini transport, tool *declarations*, and
  the tool loop for the chat assistant. It does **not** implement the tools:
  handlers are injected by [api/routes/chat.py](api/routes/chat.py), so `services/`
  never imports `api/`. Boots fine with no `GEMINI_API_KEY` and with `google-genai`
  uninstalled — `/chat` then falls back to DeepSeek and only 503s if neither is
  configured.
- [deepseek_chat.py](services/deepseek_chat.py) — DeepSeek chat fallback (raw HTTP,
  same tool-loop contract as Gemini). Configured by the shared `AI_ANALYSIS_*` env.
- [ai_analysis.py](services/ai_analysis.py) — DeepSeek deep analysis behind
  `GET /stocks/ai-analysis`; reuses `analyze_sync` plus a live quote, TTL-cached.
  The frontend currently locks this behind a "coming soon" flag
  (`VITE_AI_ANALYSIS_ENABLED`).
- [symbol_search.py](services/symbol_search.py) — fuzzy company-name → ticker search
  over the CSE listing.

### The feed split — Yahoo trains, CSE serves

The original rule — "CSE data must never reach `build_feature_row()`" — died when
Yahoo's CSE feed did. Serving on Yahoo's forward-filled tail would anchor every
prediction on a months-old bar, so serving moved to the live CSE feed. What
remains non-negotiable:

- **Features are computed only by `services/features.py`**, identically in
  training and serving. That is the real train/serve-parity guarantee; the feed
  split is allowed *because* every feature is a scale-free ratio.
- **Serving has ~5 rows.** `companyChartDataByStock` returns the same 5 daily
  bars whether you ask for `period=7` or `period=365`, which is why every feature
  window is <= 3 and why `/market/history` also serves only ~5 daily bars (the
  frontend's longer chart ranges simply show fewer points). CSE's `period=1`
  intraday tick feed *is* good and is exposed separately as `/market/intraday`.
- **The two feeds do not mean exactly the same thing.** Training bars carry a
  real Open; serving Open is previous Close. Volume semantics differ (Yahoo
  consolidated vs CSE `quantity`), which `Rel_Volume` mostly absorbs by being a
  ratio. The one measured skew is `Open_Pct` — see known limitations.

## Running — everything goes through Docker

```bash
# Start (from the backend dir). --build only needed after requirements change.
docker compose -f docker/docker-compose.yml up -d --build backend-dev
```
API on `http://localhost:8000`, Swagger at `/docs`. Build context is `..`
(`TradeVision-backend/`), since compose lives in `docker/`.

### Training the model

```bash
docker compose -f docker/docker-compose.yml exec backend-dev python -m ml.fetch_data
docker compose -f docker/docker-compose.yml exec backend-dev python -m ml.train_model
docker compose -f docker/docker-compose.yml restart backend-dev   # reload the artifact
```

Training runs **inside the container** so the model is built by the exact `xgboost`
that will serve it (`xgboost-cpu` is pinned in `requirements.txt` for the same reason).
The dev bind mount (`..:/app`) means output lands directly in your host `ml/data/` and
`models/` folders.

### Manual test scripts

```bash
docker compose -f docker/docker-compose.yml exec backend-dev python -m test.test_prediction_engine JKH.N0000
docker compose -f docker/docker-compose.yml exec backend-dev python -m test.test_news_pipeline
docker compose -f docker/docker-compose.yml exec backend-dev python -m test.test_stale_data JKH.N0000
docker compose -f docker/docker-compose.yml exec backend-dev python -m test.verify_features ml/data/JKH-N0000.CM.csv
```

## Conventions & gotchas

- **Imports are absolute from the backend root** (`services.*`, `api.*`, `ml.*`). Keep
  `PYTHONPATH` pointed at this dir; no relative-import hacks. There are no
  `__init__.py` files — the layout relies on namespace packages.
- `# pyrefly: ignore [missing-import]` comments suppress the type checker for ML libs.
- **Blocking work in routes must go through `run_in_threadpool`.** Not stylistic:
  `sync_playwright()` *raises* if started inside a running asyncio loop, and
  FinBERT/yfinance would stall the event loop.
- **`NewsSentimentPipeline` is single-use** in WEBSITE_SEARCH/BOTH mode —
  `process_news_for_stocks()` closes the scraper in a `finally`, permanently stopping
  Playwright. The API builds a fresh pipeline per request around a **shared** analyzer
  (see [api/dependencies.py](api/dependencies.py)); the scraper is cheap, FinBERT is not.
- **A missing model artifact must not crash the app.** The engine records the failure
  and the endpoint returns HTTP 200 with `price_prediction: null` and a `model_status`.
- First FinBERT run downloads ~400MB from Hugging Face. The `hf_cache` volume persists
  it across rebuilds for **both** dev and prod — don't remove those mappings.
- Scraping is network- and layout-dependent. `GOOGLE_NEWS_RSS` is the reliable default;
  website mode breaks when target sites change markup.
- FinBERT truncates at 512 tokens; the tokenizer enforces it, not a character cap.
- [test/](test/) holds **manual `__main__` scripts**, not a pytest suite. If you add real
  tests, wire up pytest and put them here.

## Deployment

`.dockerignore` excludes `ml/data/` and training outputs but **not** `models/*.json` —
the trained artifact must ship inside the image, because `backend-prod` has no bind
mount. Verify with the prod profile before shipping:

```bash
docker compose -f docker/docker-compose.yml --profile prod up -d --build backend-prod
curl "http://localhost:8000/api/v1/stocks/analyze?symbol=JKH.N0000&include_news=false"
```
`model_status: "model_not_loaded"` here (when dev worked) means the artifact never made
it into the image.

## Where to add things

- New model features → [services/features.py](services/features.py) **and retrain**. Never
  compute features anywhere else.
- New scraping source → `WEBSITE_SEARCH_TEMPLATES` in [services/scraper.py](services/scraper.py).
- More training data → add tickers to [ml/cse_universe.py](ml/cse_universe.py), re-run fetch +
  train. This does *not* change which symbols can be predicted, only how much the model
  learns from.
- Better news coverage for a ticker → add it to `_TICKERS` in
  [services/ticker_registry.py](services/ticker_registry.py) with its real company name.
- New API endpoint → a new router in [api/routes/](api/routes/), included from
  [api/main.py](api/main.py).
- New Gemini chat capability → declare the tool in `TOOL_DECLARATIONS`
  ([services/gemini_chat.py](services/gemini_chat.py)) **and** add a handler of the same
  name to `TOOL_HANDLERS` ([api/routes/chat.py](api/routes/chat.py)). A declaration with
  no handler is rejected at request time rather than failing mid-conversation.

## Known limitations (worth stating plainly)

- **Trained on Yahoo bars, served on CSE bars.** Serving moved to the live CSE feed
  (see the data contract), so `as_of` is genuinely current — but the artifact was
  trained on Yahoo history and the feeds differ in detail. The measured skew:
  serving's `Open_Pct` (previous close / close, since the CSE payload has no Open)
  is ~2x wider than training's real `Open/Close` and correlates ~0 with it, though
  97.9% of values stay inside the training p1-p99 band and feature importances are
  flat (~8% each), so the effect is bounded. The clean fix, if ever wanted:
  approximate `Open = Close.shift(1)` in the training CSVs too, and retrain.
- **Next-day direction is near the noise floor.** Beating the majority-class baseline by
  1–3% is a genuine result; anything dramatically higher usually indicates leakage.
  `ml/train_model.py` prints the baseline next to accuracy for exactly this reason.
- **Sentiment is not a model input.** The artifact takes 11 technical features;
  FinBERT blends in afterwards as `expected_return += 0.005 * score` (fully bullish
  news moves the expected return ~+0.5%). The sentiment block is returned separately
  so the fusion is visible, not hidden.
- **Unregistered tickers get weaker news.** The scraper falls back to the ticker root as
  a search term; the response includes a warning. Prediction is unaffected.
- **Prod runs `--workers 2`** — each worker loads its own FinBERT copy and its own cache.
